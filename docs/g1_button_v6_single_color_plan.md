# g1_button_v6：单色按压 + 脚本回位方案

本文取代 [g1_button_v4_supplement.md](g1_button_v4_supplement.md) 与
[g1_button_v5_training_set.md](g1_button_v5_training_set.md) 的技术路线。
前两版都在试图让策略自己走完多按钮序列，本版**把序列调度交给脚本，策略只负责"从固定位姿按一个按钮"**。
所有数字均为本机实测。

---

## 0. 三分钟快速上手（给训练侧）

**一句话原理**：策略只负责"从预备位姿按一个指定颜色的按钮"，序列调度和按完回位交给评测脚本。
这样每一段的起点都与训练数据一致，语言信号也最干净。

| 要做的 | 怎么做 |
|---|---|
| 拿数据 | `g1_button_v6`：800 集纯单色，61,621 帧，496 MB。打包好后由采集方传给你 |
| 归一化 | **必须重算**（换数据集了）：`compute_norm_stats.py --config-name pi05_g1_button_lora` |
| 训练 | `--num-train-steps 12000 --lr-schedule.decay-steps 12000`（两个都要改，只改前者会导致学习率降不到位）；24 GB 卡 `--batch-size 16` |
| 评测 | `--auto_segment --action_repeat 10 --max_steps 3000`，官方指令原样传给 `--prompt` |
| 验收 | 训完先跑离线接地探针，单色接地 ≥85% 再上仿真器 |

**三个不要**：不要和 v4/v5 混训（时序基准不同）；不要传 `--success_mode press`（几何会偏 4 厘米）；
不要用 `--action_repeat 1`（那是官方指南示例里的值，会让机器人快 10 倍、够不到按钮）。

## 1. 方案

**训练**：只用单色数据，每集"从预备位姿出发 → 按一个按钮"，指令固定为 `按X按钮`。

**评测**：脚本把官方指令解析成颜色序列，逐个下发单色指令；**每按完一个就伺服回预备位姿**，
再按下一个。这样每一段的起点都与训练数据完全一致。

```
官方指令 ──解析──▶ [绿, 红, 黄, 蓝]
                     │
   ┌─────────────────┴─────────────────┐
   │  策略：预备位姿 ──「按绿色按钮」──▶ 按下  │
   │  脚本：伺服回预备位姿                 │  × 4
   └───────────────────────────────────┘
```

### 为什么这样更优

1. **消除分布外**。之前失败的核心是：分段评测时第 2/3/4 段从"刚按完上一个按钮"的位姿开始，
   而单色训练数据全都从预备位姿出发，模型没见过。回位把每一段的起点拉回同一点。
2. **语言信号最干净**。训练退化成纯单目标任务，每一帧的颜色词都充分且必要，
   "忽略语言"的捷径解从根上不存在。
3. **回位时间正好满足官方 P2 规则**（见下节），于是按压本身可以采得很快。
4. **失败可隔离**。回位是脚本、成功率 100%；策略只做数据覆盖最充分的那一个动作。

### 合规性

指南第 1.1 节明确允许「使用自己独立编写的控制算法、规划器或策略网络替代官方脚本，
只要最终能向 `ScorerClient` 提交符合评分规则的动作结果」；第 4.2 节的技术路线表里
「直接关节控制 + HEFT 站立」的优点写的就是"已有满分参考实现"。

**红线**：禁止「非实时控制」。回位必须是**真实伺服**（`drive_to_ready` 用位置线性插值 +
姿态 slerp），**绝不能瞬移**。注意采集脚本每集起点用的是瞬移（`READY_STEPS` 注释里写明），
那是采集时的做法且不录制，**评测时照搬会踩线**。

## 2. 关键发现：官方 P2 反速通规则决定了节奏

采集脚本里实现的官方评分口径（`g1_omnipicker_collection_scripted_button_combo_lerobot.py:247-258`）：

```
OFFICIAL_STEP_SCORE  = 10.0   每个按钮满分 10 分（任务满分 40）
OFFICIAL_PEAK_M      = 0.05   末端到按钮 site 距离 0.05m 得满分，0m 与 0.10m 都只有 6 分
OFFICIAL_P1_DISCOUNT = 0.35   最佳帧上最近的不是目标按钮 → 该步 ×0.35
OFFICIAL_P2_SPAN_S   = 20.0   四钮最佳帧跨度 ≤ 20s → 全部 ×0.6
OFFICIAL_P2_FAST_S   = 5.0    跨度 ≤ 5s → 全部 ×0.4
```

**这解释了为什么 v4 的采集节奏是 9.5 秒/钮**：脚本作者按 P2 倒推（四钮跨度须 > 20s，即每钮 > 6.7s）。
本次标定实测：把接近/后撤段压短到 4.2 秒/钮时，**每次按压质量完全不变**
（official 9.05~9.44、site 距 68~74mm），但四钮跨度触发 ×0.6 折扣、整集判废。

**P2 只在"一次尝试凑满 4 个按钮"时触发**（`len(best_times_s) < 4` 直接返回 1.0），
所以**单色集怎么快都不会被折扣**——这就是本方案能同时做到"采得快"和"不丢分"的原因。

## 3. v6 数据集

采集参数（相对 v4 只改了这几项）：

```bash
python auto_collect_windows.py --out <输出目录> --total 800 --chunk 25 \
    --max_buttons 1 --length_weights 1,1,1,1 \
    --extra "--canonical_ratio 1.0 --clock sim \
             --steps_approach 200 --steps_retract 120 --steps_hold 150 \
             --repo_id local/g1_button_v6"
```

**仍然沿用 v4 默认值的关键项**：`--success_mode official`（不要传 `press`，那会多推 4 厘米、
反而扣分）、`--fps 20`、同一布局 `g1_button.json`、同一初始位姿、同一份轨迹候选 yaml。

### 实测结果

| 项 | v6 | v4 基准 |
|---|---|---|
| 规模 | **800 集 / 61,621 帧 / 499 MB** | 1000 集 / 997k 帧 / 5.7 GB |
| 保留率 | 99.0%（800/808） | — |
| 组成 | 全部单色单次按压 | 四键占 62% 帧 |
| 四色均衡 | 绿199 / 蓝201 / 红206 / 黄194 | — |
| 指令文本 | **只有 4 种，100% 规范句** | 505 种，中位每种 1 条 |
| `official_score` | **9.320** | 9.280 |
| 最佳帧距离 | 70.6 mm | 71.2 mm |
| 瞄准误差 | 15.7 mm | 16.1 mm |
| 按错按钮 / P1 扣分 | **0 / 0** | — |
| 基座漂移 | 中位 0.10 / 最大 0.40 mm | <1 mm |
| 采集速度 | **9 秒/集** | 25 秒/集（v4 单色） |

### 两项结构性改善

**帧间隔完全恒定**。改用 `--clock sim` 后：

```
帧间隔 min 0.0500s  max 0.0500s  唯一值数 = 1  →  每帧恰好 10.00 控制步
```

v4 的墙钟门控下这个值在 4.46~8.90 之间浮动（随采集机器忙闲变化），
意味着同样的画面对应差两倍的动作位移，模型只能学平均值。现在这个噪声源消失了，
**`--action_repeat` 的正确值就是 10，不用再试**。

**起点完全一致**。首帧右臂位置 `[0.5363, -0.3067, 0.2871]`，跨集标准差 **0.00 mm**，
与评测时回位后的落点严格对应。

## 4. 训练

```bash
ln -sfn <v6目录> $HF_LEROBOT_HOME/local/g1_omnipicker_button_combo

cd openpi     # 已按 openpi_patches/g1_button/README 打过补丁
uv run scripts/compute_norm_stats.py --config-name pi05_g1_button_lora

uv run scripts/train.py pi05_g1_button_lora --exp-name g1_button_v6 --overwrite \
    --num-train-steps 20000 --lr-schedule.decay-steps 20000 \
    --batch-size <显存能放下的值，24GB 卡建议 16>
```

**步数从 30000 降到 20000**：61.6k 帧跑 30000 步已是 10 个轮次，容易过拟合。
学习率衰减长度必须同步改，否则停下来时学习率还没降到位。

**不要与 v4 / v5 混训**：那两批是墙钟门控 + 慢节奏，混进来会把刚消除的时序抖动重新引入。

## 5. 评测

评测脚本新增三个参数（本分支已改）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `--auto_segment` | 关 | 把 `--prompt` 里的官方指令解析成颜色序列，逐个下发**与训练逐字一致**的 `按X按钮` |
| `--return_move_steps` | 600 | 段间回预备位姿的插值步数 |
| `--return_settle_steps` | 200 | 回位后等 OSC 收敛的步数 |

段间回位本身是脚本原有功能（`--start_pose ready` 默认开启，第 867 行），
但原来复用的是每集起点的 150+150 步，只有 1.5 秒，会让四钮跨度掉到 17.1 秒触发 P2。

```bash
python eval_g1_omnipicker_button_lerobot.py \
    --task_config ../../dataCollection/common/example.yaml \
    --host <策略服务器> --port 8010 \
    --prompt "<官方给的完整指令>" \
    --auto_segment --action_repeat 10 --max_steps 3000
```

日志会打印 `[auto_segment] 「先按绿色按钮，再按红色…」-> 按绿色按钮 | 按红色按钮 | ...`，
可直接核对文本是否与训练逐字一致。评分仍由官方 `ScorerClient` 判定，
传给 `start_attempt` 的 `targets` 与传完整指令时相同。

### P2 配速核算（按 v6 实测）

| 环节 | 仿真时长 |
|---|---|
| 一次按压（74 帧 × 10 步 × 5ms） | 3.70 s |
| 回位（600 + 200 步） | 4.00 s |
| 单次循环 | 7.70 s |
| **四钮最佳帧跨度 = 3 × 7.70** | **23.1 s** > 20 s ✅ 余量 15% |

跨度不够就加大 `--return_move_steps`，这是完全可控的参数。
`--action_repeat` 也可以调（10 是原速，调小提速、调大放慢），但调小会同时压缩跨度，两者要一起算。

## 8. 训练侧已知坑：首次存档时可能 OOM

在 HPC 的内存受限容器里实测到一个**可复现**的崩溃：训练跑到第一次保存检查点（第 1000 步）时退出，
日志里是

```
RuntimeError: DataLoader worker (pid xxxxx) is killed by signal: Killed.
```

随后跟着 orbax 的 `cannot schedule new futures after shutdown`。**后者是后果，不是原因**——
真正的原因是内核 OOM killer 杀掉了数据读取子进程。

机理：pi0.5 保存检查点要把完整权重（约 12.5 GB）从显存拷到内存，orbax 的异步存档在写盘期间
还会多留一份；再加上每个数据读取子进程都带一份 JAX 运行时（约 2 GB），内存瞬间冲高。
容器里 `top`/`free` 看到的是**宿主机**内存，不是容器配额，很容易误判为"内存充足"。
查真实配额：`cat /sys/fs/cgroup/memory.max`（v2）或 `/sys/fs/cgroup/memory/memory.limit_in_bytes`（v1）。

缓解手段（按性价比排序）：

1. **`--num-workers 1`**（甚至 0）。已经量过，这个任务是 GPU 算力受限（A100 上 3.6 秒/步，
   把数据解码完全去掉也不变快），读 JPEG 很便宜，1 个子进程完全喂得饱，却能省下好几 GB。
2. **检查点写本地盘**：`--checkpoint-base-dir /tmp/ckpt`。写网络盘慢，异步存档期间那份内存拷贝
   一直挂着；写本地盘能大幅缩短这个窗口。记得事后手动拷一份到持久存储。
3. **`--save-interval 2000`**：少几次内存尖峰。

台式机（如 4090 + 大内存）通常不会遇到。但**如果训练恰好崩在第一次保存检查点，先查这个**，
别浪费时间去查数据或终端会话——我们在这上面误判过两次。
