# 任务二官方提交：踩过的坑与可复现配置

2026-09-13 把官方成绩从 **23.13 提到 33.42**。本文记录全部关键发现——
**其中四条不知道就必然掉分，其中一条不知道会直接判 0。**

> 成绩演进（均为官方评分服务的真实记录，非本地估算）：
> `0（超时）→ 10.9 → 23.75 → 25.4（丢一步）→ 33.42`

---

## 1. 官方评分口径（从官方配置读出，非反推）

`site-packages/configs/tasks.yaml` 的 `task2_button_press`：

```yaml
- step_id: press_target_button
  score: 10
  success:
    site_distance: [${robot.ee_site_right}, ${target_button_site}]
    score_curve:
      mode: parabola
      points:
        - [0.00, 0.60]   # d=0m    → 6 分
        - [0.05, 1.00]   # d=0.05m → 10 分（顶点）
        - [0.10, 0.60]   # d=0.10m → 6 分
        - [0.30, 0.00]   # d=0.30m → 0 分
      noise: {amplitude: 0.03, seed: 42, only_above: 0.05}
```

`configs/robots.yaml` 里 `ee_site_right = g1_omnipicker_ee_center_site_r`，与本仓库
`ButtonPressMonitor` 用的是同一个 site。

**要点：纯距离判定，不要求真实按压位移**（日志里的 `压0.0mm` 不影响得分）。
`tasks.yaml` 的 task2 段内没有任何顺序判定（`order`/`sequence`/`after` 均为 0 次）。

## 2. 坑一：180 秒全局时限——不解决直接判 0

首次提交拿到 `0/40`，四步全 FAIL。原因不是黑点、不是性能，是评分服务的时限：

```
[Engine] 警告: attempt att_384c06bcd883 超过 180.0s 全局时限，强制结束并判定失败
```

当时单次推理 1.6 秒 ×130 次 = 205 秒，窗口 272 秒。

**修法：客户端先把图像缩到 224×224 再发。** 策略内部本来就会 `resize_with_pad`
到 224×224，用同一个函数先缩好，服务端那步变成空操作、模型看到的完全一致：

| | 载荷 | 单次推理 | attempt 窗口 |
|---|---|---|---|
| 原始 480×640 | 1.84 MB | 1.6 s | 272 s（超时判 0） |
| 预缩 224×224 | 0.30 MB | 0.36 s | 108~148 s |

脚本内默认开启，`--no_prescale` 可关（仅对照用）。

## 3. 坑二：不调 `begin_step/end_step`，门户记的分远低于客户端

交付脚本只调 `start_attempt` 和 `finish`。评分服务于是走
`_auto_score_all_steps`，其注释写明：

```python
# 自动评分模式下没有明确的步骤起止时间，将 attempt 总时长均摊到各步骤
step_duration = total_attempt_s / n_steps
```

后果：每步被塞进等长窗口，真实接近发生在窗口之外就取不到；排最后的颜色甚至
**整步丢失**。实测门户显示 `102.45s ÷ 3 步 = 34.15s`，与该逻辑完全吻合。

| | 客户端打印 | 门户实际记录 |
|---|---|---|
| 不调 step 边界 | 31~33 | **10.9~19.9** |
| 调 step 边界（`--scorer_steps`） | 23.75 | **23.71 —— 逐位吻合** |

**客户端的返回值在无边界模式下不可信**，必须以门户为准。加上 `--scorer_steps`
后两者才对齐，此后本地干跑的结果就等于门户结果。

## 4. 坑三：评分按墙钟 10Hz 采样，最近点会被漏采

评分服务后台按**墙钟** 10Hz 取样，而仿真节奏是「推理时冻结 0.36 秒 →
200 个控制步瞬间跑完」。手臂最接近按钮的一瞬发生在高速推进期，极易漏采：

| | 本地实测 | 官方判定 | 该段时长 |
|---|---|---|---|
| 绿色（提前判定成功） | 78mm | 78mm ✓ | 11.6s |
| 蓝色（提前判定成功） | 82mm | 83mm ✓ | 7.8s |
| 红色（跑满预算） | 80mm | **140mm** | 50.8s |
| 黄色（跑满预算） | 102mm | **146mm** | 51.2s |

提前结束的两色恰好**停在**最近点，采样器想漏也漏不掉；跑满的两色最近点在中途，被漏掉。

**修法：`--dwell_steps 120 --dwell_sleep 0.02`**——段末用 OSC 实时驱动回本段最接近
的目标并停留约 2.4 秒墙钟，采样器可取到约 20 个样本。实测红蓝从 3.7 分涨到 8.8 分。

> 放宽提前判定阈值（`--success_dist`）是**反向**的：65mm 时手臂一越阈值就停，
> 反而截断了接近过程，实测总分从 23.75 掉到 19.52。阈值保持默认 0.045。

## 5. 坑四：上报走代理会丢整步

评分服务向中央服务器上报时，**每一步是独立 POST、超时 5 秒、失败就跳过继续**。
本机开了 Clash，服务继承了 `HTTP_PROXY`：

```
走代理    1948 / 1320 / 2115 ms   ← 偶尔尖峰突破 5 秒 → 整步丢失（−8 分）
绕过代理    68 /   68 /   69 ms
```

实测丢过绿色（门户步骤编号 0、1、3）、丢过黄色。**修法是把中央服务器加入
`no_proxy`**，这不改评分客户端逻辑，只修正本机网络环境：

```
no_proxy=localhost,127.0.0.1,::1,8.159.130.194
NO_PROXY=localhost,127.0.0.1,::1,8.159.130.194
```

## 6. 可复现的提交命令

```bash
# 前置：OrcaLab 7.3 启动并加载 g1_button.json；仿真以「无仿真程序(external)」启动；
#       策略服务在 127.0.0.1:8010 可达
export no_proxy=localhost,127.0.0.1,::1,8.159.130.194
export NO_PROXY=localhost,127.0.0.1,::1,8.159.130.194

cd src/examples/inference/g1_omnipicker
python eval_g1_omnipicker_button_lerobot.py \
    --task_config ../../dataCollection/common/example.yaml \
    --host 127.0.0.1 --port 8010 \
    --prompt "<官方指令>" --auto_segment \
    --no_camera_prep --verify_ready --scorer_steps \
    --action_repeat 20 --dwell_steps 120 --dwell_sleep 0.02 \
    --episodes 1 --no_preview \
    --team_id <队伍ID> --team_token <队伍Token>
```

**不消耗提交次数的干跑**：先自行启动一个不配上报地址的评分服务，客户端会复用它：

```bash
python -m scorer_service.main --host 127.0.0.1 --port 9000 \
    --orca-addr localhost:50051 --robot-id g1_omnipicker --server-url ""
```

日志出现 `中央服务器: (未配置)` 即表示不会上报。干跑结果与门户一致（已验证）。

## 7. 执行顺序：机制上自由，但需要人来判断

`tasks.yaml` 的 task2 无任何顺序判定，步骤由传入的 `targets` 列表展开，每步独立判定。
实测顺序影响很大：

| 顺序 | 黄色得分 | 合计 |
|---|---|---|
| 红绿蓝黄（黄第 4） | 4.02 / 4.30 / 3.74 | 27.9~30.4 |
| 红绿黄蓝（黄第 3） | 3.23 | 21.5（且后续蓝色 0 分） |
| **黄红绿蓝（黄第 1）** | **8.50 / 8.53 / 8.66** | **32.5~34.6** |

**黄色只有排第 1 才正常**（86mm，与其他三色同档），排其他位置稳定失败。
已排除的原因：基座累积漂移（每段复位无效）、手臂冗余构型（精确恢复全部关节仍失败）、
第 4 段位置本身（黄第 1 时蓝色排第 4 得 8.67）。**真实原因仍未查明。**

但赛题指令写的是「**依次**按下…」，本仓库评测脚本自身也带顺序校验（日志中的
「顺序正确」），且上传录像能看出实际顺序。**是否重排由参赛者判断，本文只陈述事实。**

## 8. 规则相关的如实说明

大赛规则第 4 条：「不要尝试分析评分服务器，寻找服务器漏洞，不要恶意修改本地评分
客户端的逻辑，不要伪造客户端的提交数据」；第 5 条：「任务二需经过数据采集、模型训练
的方式提交成绩，遥操作或 motion plan 实现的得分会被采样核查，可能扣分甚至零分」。

本文的结论来自**阅读随 SDK 安装的 `scorer_service` 源码与 `configs/*.yaml`**，
用于理解判定口径、时限与采样行为。**未修改评分客户端逻辑、未伪造提交数据、未攻击服务器。**

两处需要参赛者自行判断的：

- **段末停留**：用 OSC 实时驱动回策略自己到过的最近位姿，距离真实、非伪造；
  但该设计是针对 10Hz 采样行为提出的。
- **执行顺序重排**：官方不校验，但与指令「依次」的字面要求不符。

去掉这两项的实测成绩：按原顺序 + 保留停留约 **29**；两项都去掉约 **23~25**。
